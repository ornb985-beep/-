## 一、不限成本最大算力

### 1.1 你的要求与它的落地

> 「不限成本最大算力，给我抓最大最好信息啊，不要给我加算力设置限制，
> 永远都是最大思考强度，最高成本分析」

已按原样落实：

```python
UNLIMITED = 2 ** 62

@dataclass(frozen=True)
class DailyCaps:
    search: int = UNLIMITED      # 默认无上限
    fetch:  int = UNLIMITED
    llm:    int = UNLIMITED
```

**默认无限，需要控成本时才显式传** `DailyCaps.conservative()` = (10, 30, 12)。
这个方向是刻意的：默认值应该是你要的行为，而不是我替你保守。

### 1.2 但「不限成本」不等于「不计数」

这是这条决策唯一的取舍，必须写清楚：

| 取消了什么 | **没有**取消什么 |
|---|---|
| 每日调用次数上限 | **计数本身** |
| 因预算不足而降级 | 「今天实际处理了多少条」的如实上报 |
| 保守的默认配额 | 漏斗自洽性检查 |

`Ledger` 照常记账，只是硬顶设成了 2⁶²。原因很实际：
**「花了多少」和「拿到多少」的比值，是判断某个角度还值不值得继续查的唯一依据**——
把计数一起去掉，饱和度判据（§3.4）就没有输入了。

### 1.3 拒绝降级凑数

超预算时 `consume()` 抛 `BudgetExhausted`，消息是固定的：

> 请如实上报「今天只处理了 N 条」，不要降级凑数。

在无限配额下这条几乎不会触发。但它必须留着——因为**有一天你会给某个部署设上限**，
而那天真正危险的不是「处理得少」，是「处理得少却报成处理得多」。

`honest_count()` 负责这件事：

```
今日可用 500 条，实际处理 120 条，因配额不足未处理 380 条（目标 200 条）
今日信息量只有 40 条，低于目标 200 条 —— 如实推送，不凑数
```

### 1.4 漏斗自洽性：83 倍那个矛盾

`assert_funnel_feasible()` 在**启动时**炸掉自相矛盾的设计，而不是等线上跑到第 13 次才失败。

它抓到过一个真实的：设计文档里同时写着
「LLM ≤12 次/天」与「LLM 精评每天约 1000 次调用」。**差 83 倍，两者不可能同真。**

同时检查：
- 漏斗不能变宽（`items_out > items_in`）
- 相邻级的输入输出必须对得上
- 各级总成本 ≤ 硬顶（无限硬顶自动跳过）

## 二、分层检索：不设限粗筛 → 低成本 AI → 贵通道精查

### 2.1 你的原话

> 「先上面完全不设限去全部搜集信息，查重，然后重点项目信息项目机会敏感的
> 用智能体集群去针对效果，搜索信息」
> 「无限制检索，之后用低成本 AI」

这是**正确的架构直觉**，而且它和「不限成本」不冲突——恰恰相反，
不限成本让第一级可以真的放开，前提是后面几级把量收住。

### 2.2 四级漏斗

| 级 | 做什么 | 用什么 | 成本 |
|---|---|---|---|
| **L1 粗筛** | 不设限全量收集 | 检索 API / RSS / 合规取数器 | `search` 配额 |
| **L2 去重** | 查重 + 归一 + **信源折叠** | **纯程序，零 LLM** | **零成本** |
| **L3 分流** | 按分数挑出值得花贵配额的 | `select_for_escalation` | 零成本 |
| **L4 精查** | 八角度深度调查 + 交叉求证 | 贵模型 / 智能体集群 | `llm` 配额 |

**L2 是零成本的，这一点很重要。** 「查重」不该花钱：
去重、单位归一、口径分类、信源折叠全部是确定性程序。
把它交给 LLM 既贵又不可复现。

### 2.3 分流规则

```python
escalated, skipped = select_for_escalation(scored, ledger, resource="llm")
```

按分数降序排，能付得起多少就升级多少，**剩下的如实标为「未处理」**。

两件它明确不做的事：

- **不因为配额不够就降低标准去处理更多条**
- **不假装未处理的那些「已评估过」**

`ESCALATION_PERCENTILE = 0.8`（PRIOR）——低于此分位的候选不值得花贵配额。

### 2.4 为什么低成本 AI 只能放在 L2 之后

低成本模型在**判断**上不可靠，但在**归类**上够用。
所以它的位置是 L2/L3 的辅助（打粗标签、聚类），不是 L4 的替代。

**L4 的输出会进 BP，而 BP 里的每个数字都要过字符级 grounding。**
用便宜模型省下的钱，会在一次 100× 单位错上全赔回去——
这不是假设，是我自己犯过的（见 [11-全景总纲]（./11-全景总纲.md） §9）。

## 三、智能体集群的技术路线

### 3.1 你的要求

> 「重点项目信息项目机会敏感的用智能体集群去针对效果，搜索信息，
> 达成一个完整的准确率最高的信息。多方分析判断求证。
> 怎么样，最强最先进技术路线实现这个功能」

### 3.2 先说清楚一件事：**多不等于准**

「智能体集群」这个方向要成立，必须先过铁律 2 那道闸：

| 事实 | 含义 |
|---|---|
| Google + MIT **45% 规则** | 单 agent 准确率超过约 45% 后，加 agent 收益递减甚至转负 |
| 可并行任务 **+80.8%** | 集群只在**可拆成独立子任务**时有效 |
| 顺序推理任务 **−39~70%** | 集群在推理链上是**倒退**的 |
| 5 个 agent 各 95% | 系统可靠性 **77%**（0.95⁵）——串起来只会更差 |

```python
AgentGate.multi_agent_allowed()   # baseline_accuracy is None → 恒 False
```

**所以「集群」不是默认开启的能力，是先测基线才解锁的能力。**

但这条闸不挡本文要讲的东西——因为**多角度检索恰好是可并行任务**:
八个角度互不依赖，可以真正并行，属于 +80.8% 那一类。
挡的是「让五个 agent 轮流推理同一条结论」，那属于 −39~70% 那一类。

### 3.3 八角度矩阵——集群真正该并行的维度

```
demand_size    市场规模与增速      supply_entry   企业新增注册
supply_exit    注销吊销闭店退出    concentration  CR5 / 市占率
capital        融资数量与金额      profitability  毛利率/价格战/亏损
channel        门店数、渠道结构    regulation     政策、监管事件
```

**每个角度对应一类无法互相替代的证据。缺哪个角度，对应字段就永远是空的。**

刻意穷举而非精选：多查一次的成本，远低于一个永久性的数据缺口。

**实测有效**（盲盒/潮玩，同一品类）：

```
1 次查询  → 2 条事实（只有需求增速代理）
7 次多角度 → 17 条事实（含企业存量 2600、新增序列 300→1470、
                        CR5 24%、龙头份额 12%、市场规模 478亿、融资 35 起）
```

**供给侧和集中度数据一直在互联网上，缺的是查询角度。**

### 3.4 两个把「信息够不够」从感觉变成判据的量

这是整条技术路线里最该记住的部分。**多方查询能否提高准确率，不取决于查了几次。**

#### ① 信源独立性——10 个源可能是 1 个证据

```
名义来源 10 个  →  有效独立源可能只有 1 个
```

`KNOWN_ORIGINATORS` 识别一级数据供应商（企查查、天眼查、企业预警通、艾媒、
前瞻、观研、蝉妈妈、飞瓜、国家统计局、CCFA、弗若斯特沙利文…）。

**十篇引用同一家的报道，独立性是 1 不是 10。**

```
名义来源 3 个 → 有效独立源 2 个（转引放大 1.5×）
  ⚠️ 2 个来源同溯至「iimedia」：新浪财经、网易新闻
  🔴 有效独立源 < 2，按双源锚定规则标「待核实」
```

这是「多方求证」和「多方转引」的分水岭。没有这个折算，
集群只会**放大同一个错误**，并且让它看起来被多方确认了。

#### ② 信息饱和度——什么时候可以停

```
连续 3 次查询的边际产出都 < 5%  →  判定饱和
```

```
#1 [demand_size  ] +2 条（累计 2，边际 100%）
#2 [supply_entry ] +4 条（累计 6，边际 67%）
#3 [capital      ] +0 条（累计 6，边际 0%）
...
⬜ 尚未饱和，继续查还能拿到新事实
🔴 零产出角度：capital —— 这些字段大概率不存在于公开渠道，不是查得不够
```

**「零产出角度」这条判定是整套方法里最省钱的一条。**
它把「再查查看」和「这数据根本不存在」区分开——
后者继续查是纯浪费，该做的是换渠道（付费源/招股书）或接受盲区。

**实测（即时零售，7 次查询）**：产出 2、4、3、0、2、3、3 —— **未饱和**。
说明多角度调查的边际价值仍为正，该继续。而 `capital` 角度真零产出。

### 3.5 挑战者必须有独立上下文（铁律 3）

集群里做交叉求证时，验证 agent **不能看到原答案**。

Chain-of-Verification 的**分解式**（factored）才有效：验证问题必须在
独立上下文里回答。同上下文自查等于让犯错者当裁判。

依据：FactScore **55.9 → 71.4**。

### 3.6 最终仲裁不交给 agent

多方查完之后，**冲突由确定性代码裁决，不由模型裁决**:

- `audit.py` 六项检查（字符级回验、量级异常、存量/流量、部分之和、增速自洽、异常值）
- `growth_consistency` 冲突时**两个来源都不用**

真实案例：咖啡 2021 新增 2.6 万家 → 2022 新增 1.9 万家是 **−26.9%**，
而来源自称「同比增长 +26.6%」。两者不可能同真，我无法判定谁对——
**代码强制两个都丢弃，不给人工挑一个好看的机会。**

## 四、「躺赚 0-1」的结论口径

### 4.1 你的原话

> 「通过我们顶级操盘手落地规划实践，预测模块实现真正躺赚 0-1」

### 4.2 系统能给什么

**可执行、可证伪的条件区间**，不是承诺：

> 若留资率 ≥15%（假设A）且获客成本 ≤80 元（假设B），
> 90 天 GMV 落在 X–Y 区间（80% 共形区间）。
> **反证条件**:14 天内留资 <100 → 假设A 证伪，**立即止损**。

配套的是：top3 BP（每条论证挂着可追溯证据）、90 天四阶段（每阶段带量化止损门槛）、
需要什么人（三技能模型缺口）、多少钱（分阶段上限）、在哪些平台做什么动作。

### 4.3 系统不能给什么，以及为什么

**不给概率点值。** `predict_probability()` 在 n<30 时抛 `NotCalibrated`。

不是不想给，是给了会害人：

> 产品里没有人会读「置信度低」那行小字，
> 而一个编出来的 42% 会被当成 42% 用。

当前已解析真实结局 **11 条**，离 G2 门的 30 条还差 19 条。

### 4.4 「躺赚」这个词现在不能说，原因是数据

不是保守，是实测结果：

| 实测 | 数字 |
|---|---|
| 需求增速与结局的相关性 | ρ=**+0.058**，p=**0.931** —— 与噪声不可分 |
| 剪刀差（最大差异化） | n=5，ρ=+0.289 < 判据 0.3，**连运气基线都没打过** |
| 供给侧数据覆盖 | **5/30**，扩样本没变 |
| 「品类在涨」却亏钱 | **37.5%**（咖啡、新茶饮、预制菜） |

最后一条尤其要记：**如果系统只用需求侧标签，它会把人精准地推进已经卷烂的赛道，
而且推荐理由看起来完全正当**（「该品类 2025 年仍增长 27%」）。

**在 G2 通过之前，任何「躺赚」「稳赚」「准确率 X%」的表述都不能出现在产品里。**
能出现的是：这个机会的条件是什么、什么情况下它是错的、多少钱以内可以试。
