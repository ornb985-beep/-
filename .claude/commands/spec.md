读 `docs/00-目标.md`、`docs/02-共性与独特.md`、`docs/03-什么算好.md`
（注意看我在里面改过、划掉、补充的地方——那才是我真实的想法，比你原来写的重要）。

产物：`docs/04-要做什么.md`。

**贯穿整步的一把尺子**：`docs/02-共性与独特.md` 里定的「共性必须项」一条都不能少，
「独特那一击」必须在第一版里，不许推到第二版——
推到第二版的差异化，等于没有差异化。

## 写法

### 一、用「故事」写功能，别用功能名
- ❌「客户管理模块」
- ✅「我打开它，看到今天该联系的 5 个客户，点一下就能记下刚才聊了什么」

每条故事跟一条**验收标准**：怎么算这条做好了，一句能判断真假的话。
```
- [故事] 我打开它，看到今天该跟进的客户
  [验收] 打开后 2 秒内看到列表；今天该跟进的排在最前面；没有的时候显示「今天没有待跟进」而不是空白
```

### 二、分成三档，狠一点
```
## 第一版必须有（少一个这东西就没用）
## 第二版再说（有了更好，但现在没有也能用）
## 明确不做（写清为什么不做）
```
**第一版最多 5 条。** 超过 5 条你就是没想清楚，回去砍。
砍的时候用两把刀：`docs/03-什么算好.md` 里我选的取舍，
和 `references/框架库.md` 里的「价值主张画布」（右边有、左边没有的，都是自嗨功能）。

### 三、把「东西长什么样」画出来
用纯文字画个草图，让我能想象出来。
（内容类项目就画分镜/结构大纲，服务类就画客户从头到尾会经历什么。）
像这样：

```
┌─────────────────────────────┐
│  今天要跟进的 (3)            │
├─────────────────────────────┤
│  张总 · 上次聊了报价         │
│  李姐 · 说下周再说           │
│  [+ 记一笔]                  │
└─────────────────────────────┘
```

这一步别嫌土，文字草图能暴露出 80% 的想当然。

### 四、列出「数据长什么样」
用白话说清要存哪些信息，例如：
「每个客户要记：名字、电话、上次联系时间、聊了什么、下次什么时候联系」。
不要写数据库表结构，写人话。

### 五、边界情况
列 5 条「万一……怎么办」：网断了怎么办、数据填一半退出怎么办、
同一个客户录两遍怎么办。这些不写清楚，后面全是坑。

---

写完告诉我：
- 你砍掉了什么，为什么砍
- 第一版做出来大概需要多久（给个范围）
- 哪一条你觉得我可能会不同意

然后停下。等我拍板。

## 文档末尾必须有验收单

```
## 怎么验收这一步
- [ ] 第一版不超过 5 条
- [ ] 每条都能想象出画面，不是功能名词
- [ ] 每条的验收标准，我不用懂技术就能判断真假
- [ ] 共性必须项一条不少，独特那一击在第一版里
- [ ] 【致命项】砍掉的东西里，至少有一样让我有点舍不得
      （一点都不心疼说明没真砍）
```
